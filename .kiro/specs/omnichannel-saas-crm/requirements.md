# Requirements Document

## Introduction

This document defines the requirements for an enterprise-grade Omnichannel SaaS CRM platform built on the Cloudflare ecosystem. The platform enables multi-tenant organizations to manage customer relationships, communicate via WhatsApp (both automated and official broadcast channels), handle SaaS subscription billing through iPaymu, and store all data securely using Cloudflare's edge infrastructure. Authentication and multi-tenancy are powered by Clerk Organizations with RBAC.

## Glossary

- **CRM_Platform**: The Omnichannel SaaS CRM application running on Cloudflare Workers with Hono Framework
- **Tenant**: An organization workspace identified by a Clerk Organization ID, representing one paying customer of the SaaS platform
- **Clerk_Auth_Service**: The Clerk authentication and organization management service providing user authentication, RBAC, and multi-tenancy via Clerk Organizations
- **D1_Database**: Cloudflare D1 SQL database storing CRM transactional data, contacts, billing records, and message logs
- **KV_Store**: Cloudflare KV storage used for caching tokens, sessions, rate-limits, and Clerk Org ID to Tenant ID mappings
- **R2_Storage**: Cloudflare R2 object storage for documents, payment proofs, and WhatsApp media files
- **Message_Queue**: Cloudflare Queues service used to queue WhatsApp broadcast messages to avoid gateway overload
- **GoWa_Gateway**: The Go-Wa (by Aldikemal) WhatsApp gateway server used for daily operational agent automation
- **Meta_Cloud_API**: The WhatsApp Business Official API (Meta Cloud API) used for large-scale official broadcasts with blue checkmark verification
- **iPaymu_Service**: The iPaymu payment gateway used for SaaS subscription transactions, invoice automation, and split payment
- **Payment_Link**: A redirect or inquiry URL generated by the iPaymu API for tenant subscription upgrades or quota purchases
- **Webhook_Callback**: An HTTP callback sent by iPaymu to Cloudflare Workers after a payment is completed
- **Broadcast_Quota**: A purchasable allocation of official WhatsApp broadcast messages available to a Tenant
- **RBAC**: Role-Based Access Control managed through Clerk Organizations defining permissions per user within a Tenant

## Requirements

### Requirement 1: Multi-Tenant Authentication and Organization Management

**User Story:** As a platform administrator, I want tenants to be isolated through Clerk Organizations with role-based access, so that each organization's data and users are securely separated.

#### Acceptance Criteria

1. WHEN a user attempts to access the CRM_Platform, THE Clerk_Auth_Service SHALL authenticate the user and return a session token that contains the user's Clerk Organization ID and is valid for the configured session duration (default: 3600 seconds)
2. WHEN a user is authenticated, THE CRM_Platform SHALL resolve the Clerk Organization ID to a Tenant identifier by first checking the KV_Store cache and, on cache miss, querying D1_Database, then scope all subsequent data access to that Tenant
3. THE KV_Store SHALL cache the mapping between Clerk Organization ID and Tenant ID with a configurable time-to-live (default: 300 seconds, minimum: 60 seconds, maximum: 86400 seconds)
4. WHEN a user performs an action requiring authorization, THE CRM_Platform SHALL verify the user's RBAC permissions through Clerk_Auth_Service before executing the action
5. IF an unauthenticated request is received, THEN THE CRM_Platform SHALL reject the request with a 401 Unauthorized response and include no application data in the response body
6. IF a user lacks the required RBAC permission for an action, THEN THE CRM_Platform SHALL reject the request with a 403 Forbidden response indicating the permission that was required
7. IF the Clerk Organization ID from an authenticated session cannot be resolved to a Tenant identifier in either the KV_Store or D1_Database, THEN THE CRM_Platform SHALL reject the request with a 403 Forbidden response and log the unresolved organization ID for administrative review

### Requirement 2: Contact Management

**User Story:** As a CRM user, I want to manage customer contacts within my organization's workspace, so that I can maintain an up-to-date directory of all customer relationships.

#### Acceptance Criteria

1. WHEN a user creates a new contact, THE CRM_Platform SHALL store the contact record in D1_Database scoped to the user's Tenant, requiring at minimum: full name, and at least one of phone number or email address
2. WHEN a user retrieves contacts, THE CRM_Platform SHALL return only contacts belonging to the user's Tenant, paginated with a maximum of 50 contacts per response page
3. WHEN a user updates a contact record, THE CRM_Platform SHALL persist the changes in D1_Database and record the modification timestamp
4. WHEN a user deletes a contact, THE CRM_Platform SHALL remove the contact record from D1_Database for the user's Tenant
5. IF a contact phone number does not conform to E.164 international format (1 to 15 digits with leading '+'), THEN THE CRM_Platform SHALL reject the create or update request with an error indicating the invalid phone number format
6. IF a create or update request is missing required contact fields, THEN THE CRM_Platform SHALL reject the request with an error indicating which required fields are absent

### Requirement 3: WhatsApp Operational Messaging via Go-Wa Gateway

**User Story:** As a CRM agent, I want to send and receive WhatsApp messages through the Go-Wa gateway for daily customer interactions, so that I can communicate with customers in real-time without relying on the official API quota.

#### Acceptance Criteria

1. WHEN a CRM agent sends a message to a contact, THE CRM_Platform SHALL forward the message to GoWa_Gateway for delivery and set the initial delivery status to "sent"
2. WHEN GoWa_Gateway receives an incoming message from a customer whose phone number matches an existing contact, THE CRM_Platform SHALL store the message in D1_Database linked to the corresponding contact and Tenant
3. WHEN a WhatsApp media file is received via GoWa_Gateway, THE CRM_Platform SHALL upload the media to R2_Storage under the Tenant's namespace and store the reference URL in the message record
4. IF GoWa_Gateway does not respond within 10 seconds, THEN THE CRM_Platform SHALL return an error response to the agent indicating the delivery failure, set the message delivery status to "failed", and log the event in D1_Database
5. THE CRM_Platform SHALL store all outbound and inbound messages in D1_Database with sender, recipient, timestamp, message type (one of: text, image, video, audio, document), and delivery status (one of: sent, delivered, read, failed)
6. IF GoWa_Gateway receives an incoming message from a phone number that does not match any existing contact within the Tenant, THEN THE CRM_Platform SHALL store the message in D1_Database with the sender phone number and mark it as unlinked
7. IF a received media file exceeds 16 MB, THEN THE CRM_Platform SHALL discard the media binary, store the message record in D1_Database without a media URL, and flag the record as having an oversized attachment

### Requirement 4: Official WhatsApp Broadcast via Meta Cloud API

**User Story:** As a marketing manager, I want to send large-scale official WhatsApp broadcasts using the Meta Cloud API, so that messages are delivered with the business blue checkmark and reach customers at scale.

#### Acceptance Criteria

1. WHEN a user initiates a broadcast to a list of 1 to 10,000 contacts, THE CRM_Platform SHALL validate that the Tenant's Broadcast_Quota is sufficient for the total number of contacts and enqueue each message individually into Message_Queue
2. WHILE Message_Queue contains pending broadcast messages, THE CRM_Platform SHALL dequeue and send messages to Meta_Cloud_API at a maximum rate of 80 messages per second per Tenant
3. WHEN Meta_Cloud_API returns a success acknowledgement for a broadcast message, THE CRM_Platform SHALL update the message delivery status to "delivered" in D1_Database
4. IF Meta_Cloud_API returns a rate-limit error, THEN THE CRM_Platform SHALL re-enqueue the message with an exponential backoff delay starting at 1 second, doubling on each retry, up to a maximum delay of 300 seconds, for a maximum of 5 retry attempts
5. IF a Tenant's Broadcast_Quota is exhausted, THEN THE CRM_Platform SHALL reject new broadcast requests with an error response indicating that additional quota must be purchased
6. THE CRM_Platform SHALL deduct one unit from the Tenant's Broadcast_Quota for each message successfully enqueued for broadcast
7. IF Meta_Cloud_API returns a permanent delivery failure for a broadcast message (such as invalid recipient or account blocked), THEN THE CRM_Platform SHALL mark the message status as "failed" in D1_Database and not re-enqueue the message
8. IF a broadcast message exceeds the maximum of 5 retry attempts, THEN THE CRM_Platform SHALL mark the message status as "failed" in D1_Database and not re-enqueue the message

### Requirement 5: SaaS Subscription and Billing via iPaymu

**User Story:** As a tenant administrator, I want to manage my subscription plan and purchase additional broadcast quota through iPaymu, so that I can upgrade my plan and pay seamlessly.

#### Acceptance Criteria

1. WHEN a Tenant requests a subscription upgrade or Broadcast_Quota purchase, THE CRM_Platform SHALL call iPaymu_Service API to generate a Payment_Link with an expiration time of 24 hours from creation
2. WHEN a Payment_Link is generated, THE CRM_Platform SHALL return the Payment_Link URL to the user for redirect-based payment
3. WHEN iPaymu_Service sends a Webhook_Callback indicating successful payment, THE CRM_Platform SHALL validate the callback signature for authenticity
4. WHEN a valid payment Webhook_Callback is received for a subscription upgrade, THE CRM_Platform SHALL immediately activate the new subscription tier for the Tenant in D1_Database and record the activation timestamp
5. WHEN a valid payment Webhook_Callback is received for a Broadcast_Quota purchase, THE CRM_Platform SHALL credit the purchased quota to the Tenant's account in D1_Database
6. IF iPaymu_Service Webhook_Callback signature validation fails, THEN THE CRM_Platform SHALL reject the callback and log a security alert
7. THE CRM_Platform SHALL store all payment transaction records in D1_Database including amount, status, Tenant, and timestamp
8. IF iPaymu_Service API fails to generate a Payment_Link or is unreachable, THEN THE CRM_Platform SHALL return an error response to the user indicating the payment service is unavailable and log the failure details
9. WHEN a valid payment Webhook_Callback is received indicating a failed or cancelled payment, THE CRM_Platform SHALL update the corresponding transaction record status in D1_Database to reflect the failure and retain the Tenant's current subscription tier and quota unchanged

### Requirement 6: File and Media Storage

**User Story:** As a CRM user, I want to upload and retrieve documents and media files, so that I can attach files to contacts and conversations.

#### Acceptance Criteria

1. WHEN a user uploads a file, THE CRM_Platform SHALL store the file in R2_Storage under the Tenant's namespace
2. WHEN a user requests a stored file, THE CRM_Platform SHALL generate a presigned URL from R2_Storage with an expiration time of 60 minutes for secure download
3. THE CRM_Platform SHALL enforce a file size between 1 byte and 16 MB per upload, and a maximum filename length of 255 characters
4. IF a file upload exceeds the maximum size, is zero bytes, or has a filename exceeding 255 characters, THEN THE CRM_Platform SHALL reject the upload with an error indicating the specific validation failure
5. THE CRM_Platform SHALL store file metadata (filename, content type, size, Tenant ID, upload timestamp) in D1_Database
6. THE CRM_Platform SHALL accept only files with content types matching image, video, audio, PDF, or document formats, and SHALL reject uploads with disallowed content types with an error indicating the accepted formats
7. IF a user requests a file that does not exist or does not belong to the user's Tenant, THEN THE CRM_Platform SHALL return an error indicating the file was not found

### Requirement 7: Rate Limiting and Caching

**User Story:** As a platform operator, I want API rate limiting and efficient caching, so that the platform remains performant and protected from abuse.

#### Acceptance Criteria

1. THE CRM_Platform SHALL enforce per-Tenant API rate limits using counters stored in KV_Store, where the rate limit window and maximum request count are configurable per tenant tier
2. IF a Tenant exceeds the configured API rate limit, THEN THE CRM_Platform SHALL reject subsequent requests with a 429 Too Many Requests response that includes the remaining seconds until the rate window resets, until the rate window resets
3. THE KV_Store SHALL cache Tenant configuration, contact records, and organization-to-tenant mappings with a configurable time-to-live between 60 seconds and 3600 seconds to reduce D1_Database load
4. WHEN cached data in KV_Store expires, THE CRM_Platform SHALL fetch fresh data from D1_Database on the next request and write the result back to KV_Store with the configured time-to-live
5. IF KV_Store is unreachable, THEN THE CRM_Platform SHALL bypass caching and rate limiting and serve requests directly from D1_Database while logging the KV_Store unavailability event

### Requirement 8: Message Logging and Audit Trail

**User Story:** As a compliance officer, I want all messaging activity logged with full audit trails, so that the organization can review communication history and meet regulatory requirements.

#### Acceptance Criteria

1. THE CRM_Platform SHALL log every inbound and outbound WhatsApp message in D1_Database with message ID, Tenant ID, sender, recipient, channel (GoWa or Meta), timestamp, and delivery status
2. WHEN a message delivery status changes, THE CRM_Platform SHALL update the corresponding log entry in D1_Database with the new status (one of: queued, sent, delivered, read, or failed) and the timestamp of the status transition
3. THE CRM_Platform SHALL retain message logs for a minimum of 12 months per Tenant
4. WHEN a user with audit permissions queries message logs, THE CRM_Platform SHALL return results filtered by Tenant, sorted by timestamp in descending order, with a default page size of 50 records and a maximum page size of 200 records, and support filtering by date range, channel, sender, recipient, and delivery status
5. IF an audit log query returns no matching records, THEN THE CRM_Platform SHALL return an empty result set with a total count of zero

### Requirement 9: Tenant Data Isolation

**User Story:** As a security engineer, I want strict data isolation between tenants, so that no tenant can access another tenant's data under any circumstances.

#### Acceptance Criteria

1. THE CRM_Platform SHALL include the Tenant ID, derived from the authenticated session's Clerk Organization ID, in every D1_Database read and write operation as a mandatory filter or scope condition
2. THE CRM_Platform SHALL namespace all R2_Storage paths with the Tenant ID as the root prefix to prevent cross-tenant file access
3. THE CRM_Platform SHALL scope all KV_Store keys with the Tenant ID prefix
4. IF a request attempts to access resources where the resource's Tenant ID does not match the authenticated session's Tenant ID, THEN THE CRM_Platform SHALL reject the request with a 403 Forbidden response and log the access violation including the requesting user ID, the requested resource identifier, the source Tenant ID, and the target Tenant ID to D1_Database
5. WHILE processing asynchronous jobs from Message_Queue or Webhook_Callback events, THE CRM_Platform SHALL enforce the same Tenant ID scoping rules on all D1_Database, R2_Storage, and KV_Store operations as applied to synchronous requests

### Requirement 10: Webhook Security and Idempotency

**User Story:** As a platform developer, I want webhook processing to be secure and idempotent, so that duplicate or malicious webhook deliveries do not corrupt application state.

#### Acceptance Criteria

1. WHEN a Webhook_Callback is received from iPaymu_Service, THE CRM_Platform SHALL validate the request signature using the shared secret before performing any state-changing operations or idempotency lookups
2. THE CRM_Platform SHALL store processed webhook event IDs in D1_Database with a retention period of at least 90 days to detect duplicates
3. IF a duplicate Webhook_Callback is received (same event ID already processed), THEN THE CRM_Platform SHALL return a 200 OK response without reprocessing the event
4. IF Webhook_Callback signature validation fails, THEN THE CRM_Platform SHALL return a 401 Unauthorized response and log the rejected attempt including source IP address, timestamp, and the received signature value
5. IF a Webhook_Callback is received with a missing or empty event ID, THEN THE CRM_Platform SHALL return a 400 Bad Request response without processing the payload and log the malformed request including source IP address and timestamp
6. WHEN a Webhook_Callback is successfully validated and processed, THE CRM_Platform SHALL respond within 5 seconds to prevent delivery timeout retries from iPaymu_Service
